# 新机器最小编译与执行方案

本文给出当前版本在新机器上的最短可靠部署路径。目标是让一台已经安装 ROS Noetic的 Ubuntu 20.04 x86_64 机器完成：依赖安装、Livox-SDK2 安装、干净编译、产物验证和首次启动。

新机器统一使用标准 catkin 布局：

```text
~/catkin_ws/
├── src/       # 本仓库源码内容
├── build/     # 目标机器本地生成，不放入源码包
└── devel/     # 目标机器本地生成，不放入源码包
```

源码包只应包含 `src/` 下的项目内容，不应包含已有的 `build/`、`devel/`、`install/`
或 CMake 缓存。

## 1. 已验证结论

2026-08-17 已在全新的标准 catkin 工作区进行验证，构建环境只加载系统 Noetic：

```text
CMAKE_PREFIX_PATH=/opt/ros/noetic
```

使用以下命令完成无缓存全量 Release 编译，返回码为 `0`：

```bash
catkin_make -j2 -l2 -DROS_EDITION=ROS1 -DCMAKE_BUILD_TYPE=Release
```

验证结果：

- catkin 顶层构建 16 个包；源码中共有 17 个 `package.xml`，其中一个是 LIO 内嵌的
  `livox_ros_driver` 消息子包；
- `livox_ros_driver2_node`、LIO 建图/定位、Ranger 底盘、速度仲裁、碰撞监控、
  `runnav` 和 `TagCtl` 均成功生成；
- GUI 所需 PyQt5、OpenCV、NumPy、pyserial 和当前工作区生成的 Python 消息均可导入；
- 当前源码的消息生成目标依赖完整，**新机器不需要额外修改 CMakeLists.txt**。

验证环境已经具备所列系统依赖和 Livox-SDK2 1.3.1；新机器仍需按下文检查并安装
依赖和 SDK。

## 2. 前提

本文假设：

- Ubuntu 20.04 x86_64；
- ROS Noetic 已安装，以下命令成功输出 `noetic`；
- 已取得当前版本的纯源码；
- 能使用 apt；Livox-SDK2 可在线下载或已准备离线源码包。

```bash
source /opt/ros/noetic/setup.bash
rosversion -d
```

如果是 Melodic、ROS 2、Ubuntu 22.04/24.04、ARM 或 Jetson，不属于本最小方案的已验证范围。

## 3. 放置源码

```bash
mkdir -p ~/catkin_ws/src
```

把本仓库根目录中的源码内容复制到 `~/catkin_ws/src`。复制后应类似：

```text
~/catkin_ws/src/
├── cmd_vel_arbiter/
├── collision_monitor/
├── hardware/
├── livox_ros_driver2/
├── nav/
├── ranger_ros/
├── robot_r/
├── script/
├── slam/
└── ugv_sdk/
```

如果来源目录包含已有构建产物，推荐用 rsync 排除：

```bash
rsync -a \
  --exclude='build/' \
  --exclude='devel/' \
  --exclude='install/' \
  --exclude='log/' \
  /实际源码目录/ ~/catkin_ws/src/
```

确认包文件：

```bash
find ~/catkin_ws/src -name package.xml -print
```

当前版本应找到 17 个 `package.xml`。

## 4. 安装最小依赖

即使机器已有 Noetic，仍可能没有 PCL、OpenCV、Qt、glog、TBB、APR、ASIO 和 GUI
运行依赖。

```bash
sudo apt update
sudo apt install -y \
  build-essential \
  cmake \
  git \
  pkg-config \
  rsync \
  python3-rosdep \
  libasio-dev \
  libapr1-dev \
  libboost-all-dev \
  libeigen3-dev \
  libopencv-dev \
  libpcl-dev \
  libgoogle-glog-dev \
  libgflags-dev \
  libyaml-cpp-dev \
  libtbb-dev \
  qtbase5-dev \
  python3-pyqt5 \
  python3-opencv \
  python3-numpy \
  python3-serial \
  gnome-terminal \
  can-utils
```

初始化 rosdep。已经初始化过的机器不要重复执行 `sudo rosdep init`：

```bash
if [ ! -f /etc/ros/rosdep/sources.list.d/20-default.list ]; then
  sudo rosdep init
fi
rosdep update
```

安装 ROS 包依赖：

```bash
source /opt/ros/noetic/setup.bash
cd ~/catkin_ws
rosdep install \
  --from-paths src \
  --ignore-src \
  --rosdistro noetic \
  --skip-keys='livox_ros_driver GTSAM' \
  -r -y
```

两个 skip key 的原因：

- `livox_ros_driver` 是 LIO 源码内嵌的旧版消息包，不从 apt 安装；
- `GTSAM` 仍在 package 声明中，但当前 CMake/源码没有查找或链接它。

检查时看到这两个 key 无 rosdep 定义是已知现象，其他缺失依赖不能直接忽略：

```bash
rosdep check --from-paths src --ignore-src -r
```

## 5. 安装 Livox-SDK2 1.3.1

先检查：

```bash
test -f /usr/local/include/livox_lidar_api.h \
  && echo 'Livox SDK header: OK' \
  || echo 'Livox SDK header: MISSING'

test -f /usr/local/lib/liblivox_lidar_sdk_static.a \
  && echo 'Livox SDK static library: OK' \
  || echo 'Livox SDK static library: MISSING'
```

两项都为 `OK` 时可跳过安装。缺失时安装已验证版本：

```bash
cd /tmp
git clone --depth 1 --branch v1.3.1 \
  https://github.com/Livox-SDK/Livox-SDK2.git
cd Livox-SDK2
mkdir build
cd build
cmake -DCMAKE_BUILD_TYPE=Release ..
make -j2
sudo make install
sudo ldconfig
```

离线机器应复制 Livox-SDK2 `v1.3.1` 源码，并在目标机器本地执行相同的 CMake、make
和 install 步骤。不要只复制另一台机器编译出的静态库。

## 6. 干净编译

打开新终端，只加载系统 ROS，不要先 source 其他工作区：

```bash
source /opt/ros/noetic/setup.bash
cd ~/catkin_ws
echo "$CMAKE_PREFIX_PATH"
```

首次编译时最好只看到 `/opt/ros/noetic`。开始编译：

```bash
catkin_make \
  -j2 \
  -l2 \
  -DROS_EDITION=ROS1 \
  -DCMAKE_BUILD_TYPE=Release
```

必须保留 `-DROS_EDITION=ROS1`，否则 Livox 驱动可能进入 ROS 2 CMake 分支。

LIO-Lite 在 93%～100% 附近编译时间较长，持续没有新输出不代表卡死。内存不足并出现
`Killed signal terminated program cc1plus` 时改用：

```bash
catkin_make \
  -j1 \
  -l1 \
  -DROS_EDITION=ROS1 \
  -DCMAKE_BUILD_TYPE=Release
```

不要在完整工作区运行 `src/livox_ros_driver2/build.sh ROS1`；它面向独立驱动工作区，
可能清理上级目录中的构建结果。

## 8. 运行前准备

### 8.1 用户名和地图目录

工作区路径始终使用 `~/catkin_ws`，地图数据使用 `~/maps`：

```bash
mkdir -p ~/maps
```

当前源码和 launch 中仍可能存在固定绝对用户目录。部署到任意账号前，都应先查找并把业务数据路径统一为 `~/maps`，最好通过 ROS 参数或用户目录展开实现。否则编译虽然成功，建图保存、地图加载、点位和拓扑仍可能在运行时失败。

检查固定绝对路径：

```bash
grep -RInE '/home/[^/]+/' ~/catkin_ws/src \
  --exclude-dir=build --exclude-dir=devel --exclude-dir=.git
```

运行导航前，`~/maps` 至少需要当前环境对应的：

```text
GlobalMap.pcd
FeatureMap.pcd
split_map/（启用分块定位时）
map.pgm
map.yaml
robot_positions.txt
topology.yaml
autonav_params.yaml（可选）
```

### 8.2 MID360s 网络

当前真机配置文件：

```text
~/catkin_ws/src/robot_r/config/MID360s_config.json
```

当前值：

```text
电脑雷达网口：192.168.1.5/24
MID360s：      192.168.1.167
```

先识别实际有线网口，例如 `enp1s0`：

```bash
ip -br link
nmcli device status
export LIVOX_IFACE=enp1s0
```

首次创建持久连接：

```bash
sudo nmcli connection add \
  type ethernet \
  ifname "$LIVOX_IFACE" \
  con-name livox-mid360s \
  ipv4.method manual \
  ipv4.addresses 192.168.1.5/24 \
  ipv4.never-default yes \
  ipv6.method disabled
sudo nmcli connection up livox-mid360s
```

验证：

```bash
ip route get 192.168.1.167
ping -I "$LIVOX_IFACE" -c 3 -W 1 192.168.1.167
```

不要假定网口一定叫 `enp1s0`，也不要让 Wi-Fi 和雷达网口同时占用
`192.168.1.0/24`。如果雷达 IP 已被修改，应同步修改 JSON。

### 8.3 CAN 和串口权限

```bash
sudo usermod -aG dialout "$USER"
```

注销并重新登录后配置 CAN：

```bash
sudo ip link set can0 up type can bitrate 500000
ip -details link show can0
```

MM3V 默认使用 `/dev/ttyUSB0`、38400。端口不同可在 launch 时覆盖。

## 9. 最小执行

### 9.1 推荐：启动 GUI

```bash
source /opt/ros/noetic/setup.bash
source ~/catkin_ws/devel/setup.bash
cd ~/catkin_ws
python3 src/script/aNAV_ranger.py
```

GUI 启动后按顺序操作：CAN → 底盘 → 定位 → 自动导航。第一次实车运行前先阅读
[操作手册](OPERATIONS.md)，确认物理急停、地图、TF 和碰撞监控状态。

### 9.2 命令行启动链

每个终端都先执行：

```bash
source /opt/ros/noetic/setup.bash
source ~/catkin_ws/devel/setup.bash
```

先单独验证雷达：

```bash
roslaunch robot_r msg_MID360s.launch
```

另一个终端检查：

```bash
rostopic hz /livox/lidar
rostopic hz /livox/imu
```

确认后关闭单独驱动，再按顺序启动实车系统：

```bash
# 终端 1：底盘，同时包含速度仲裁和碰撞监控
roslaunch ranger_bringup ranger_mini_v2.launch

# 终端 2：MID360s、地图、LIO 定位和 RViz
roslaunch robot_r 3startlocation.launch

# 终端 3：MoveBase、代价地图和 B 样条局部规划
roslaunch robot_r 5nav.launch

# 终端 4：拓扑 AutoNAV
roslaunch robot_r 3navlocations.launch
```

## 11. 可接受的已知编译警告

本次干净编译中出现但未阻止成功构建的警告：

- PCL 引入的部分 VTK 工具目标文件不存在；
- LIO `catkin_package()` 对 EIGEN3/PCL 变量的声明警告；
- `obstacle_detection` 在没有自定义消息时调用 `generate_messages()`；
- 内嵌 `livox_ros_driver` 生成 EusLisp manifest 时提示不在顶层工作区；
- LIO/pcd2pgm 的 deprecated、unused、signedness 和 printf 类型警告。

判断标准是最终 `catkin_make` 返回码必须为 0。任何 `fatal error`、链接失败、
`cc1plus` 被杀或目标缺失都不能当作可忽略警告。

## 12. 最常见失败

### 找不到 Livox SDK

确认：

```bash
ls -l /usr/local/include/livox_lidar_api.h
ls -l /usr/local/lib/liblivox_lidar_sdk_static.a
```

缺失时重新执行第 5 节。

### CMake 查找 ROS 2 包

如果报 `ament_cmake_auto` 或 `rosidl_default_generators`，说明未传
`-DROS_EDITION=ROS1`，或旧 CMake 缓存进入了 ROS 2 分支。应清理目标工作区自己的
`build/devel` 后按第 6 节重新编译，不要复用其他工作区的构建缓存。

### 编译成功但地图/定位失败

优先检查固定绝对地图路径、PCD/二维地图是否属于当前环境，以及 `map.yaml`、点位和
topology 是否配套。

### GUI 点击“启动 CAN”失败

GUI 的 CAN 启动逻辑位于：

```text
~/catkin_ws/src/script/aNAV_ranger.py
```

其中 `start_can()` 的 `can_command` 当前带有一个调试阶段写死的 sudo 密码，并固定
执行：

```bash
sudo ip link set can0 up type can bitrate 500000
```

部署到新机器后，应在目标机器本地找到 `start_can()`，把 `can_command` 中写死的密码
改成该机器部署账号的实际 sudo 密码。这里只修改密码字符串，不要改动 `can0` 和
`500000`，除非实际 USB-CAN 接口或底盘 bitrate 确实不同。Python 文件修改后不需要
重新执行 `catkin_make`，关闭并重新启动 GUI 即可生效。

真实密码不得写入本文档，也不要随源码提交到 Git；该项修改只能作为每台目标机器的
本地部署配置。长期部署建议进一步把 CAN 初始化改为受限的系统服务或专用授权规则，
避免在 Python 源码中保存明文密码。

如果修改密码后仍然失败，再在终端检查 CAN 设备和状态：

```bash
sudo modprobe gs_usb
ip -details link show type can
sudo ip link set can0 up type can bitrate 500000
ip -details link show can0
candump can0
```

正常状态应包含 `state UP` 和 `bitrate 500000`。如果适配器名称不是 `can0`，还需要
同步修改 GUI 健康检查和 `ranger_mini_v2.launch` 的 `port_name`，不能只改其中一处。

### GUI 找不到消息或 ROS 包

确认先完成全量编译并执行：

```bash
source /opt/ros/noetic/setup.bash
source ~/catkin_ws/devel/setup.bash
```

再从 `~/catkin_ws` 启动 GUI。
